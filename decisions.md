## 2026-08-11 — Numeric first argument always means GitHub issue number

Issue: 3b972d662ff3806793d4ebabb9ce8df8
Decision: A purely numeric first argument passed to `/brainstorm`, `/analyze-issue`, or `/letsgo` is always interpreted as a GitHub issue number, not a manual KEY. The command fetches the issue via `gh issue view` and materializes it into `specs/{NUMBER}.md`.
Rationale: Simplifies the workflow by allowing developers to use GitHub Issues directly as the entry point for the spec-driven workflow, without needing to manually create light spec files first.
Alternatives considered: (1) Introduce a new flag like `--issue` to disambiguate — rejected to keep the interface minimal and because numeric-only keys are rare in practice. (2) Check if the numeric key corresponds to an existing file first — rejected because it would create ambiguous behavior and silently override user intent.
Scope: repo-wide — affects all commands that accept a first argument as a KEY or FILE_PATH (`brainstorm.md`, `analyze-issue.md`, `letsgo.md`)

## 2026-10-06 — /letsgo automation hardening for AI Software Factory

Issue: Auto OpenCode Flow v1 design (Notion)
Decision: `/letsgo` receives six new flags: `--headless` (converts all human prompts to structured stops), `--strict-tests` (test failures after fix budget stop the pipeline; default true under headless), `--make-ci` (requires `make ci` target as the test gate), `--spec-confidence N` (escalate only conflicts with confidence >= N), `--no-auto-commit` (existing). Feature branch is created in Step 0.1 before any implementation runs. Post-review test re-run catches regressions from code-fixer changes. `specs/` files excluded from `git add` during PR creation. Agent allow-lists updated: `make *` added to `spec-implementer` and `dod-evaluator`. Models upgraded: `spec-conflict-checker` and `code-reviewer` moved from deepseek-v4.1-flash to qwen3.8-flash.
Rationale: Real /letsgo runs across venovate-vmg2 (10+ pipeline executions) revealed blocking human prompts preventing unattended operation, test gate not blocking PRs, branch created too late (main contamination risk), code-fixer changes never re-tested, spec checker producing false positives on cheap model, and make commands blocked by permission rules. These changes enable scheduled, headless pipeline runs for an AI Software Factory.
Alternatives considered: (1) External driver script for control flow — deferred to v2; the command-level approach is simpler for now. (2) Remote CI loop with fix agent — out of scope for command; belongs in a driver/scheduler layer. (3) Strict tests always on by default — rejected; breaks existing workflows that rely on the advisory gate.
Scope: repo-wide — affects `letsgo.md`, all agent files, `SKILL.md`

## 2026-10-09 — /brainstorm is Notion-URL-only and project-scoped

Issue: Auto OpenCode Flow — Notion-to-issues front end
Decision: `/brainstorm` now accepts **only** a Notion page URL and operates at project scope, not issue scope. It fetches the brief via the Notion MCP `fetch` tool, grills the user in rounds over a design tree until the frontier is empty, breaks the confirmed vision into tracer-bullet vertical slices, quizzes the user on the breakdown, then publishes each slice as a light GitHub issue in dependency order and places it on a Project board. It writes **no** files under `specs/` — the GitHub issues are the light specs, and `/analyze-issue <N>` / `/letsgo <N>` generate the deep spec per issue later. The vision, its settled decisions, and the slice breakdown persist to Engram only (`vision/{PROJECT_SLUG}/{source,decisions,breakdown}`, scope `project`). Blocking edges are expressed as `## Blocked by` text in the issue body, not as native sub-issues or a ProjectV2 custom field. The linked Project is detected via GraphQL `repository.projectsV2` on every run and never cached; when absent it is created and linked in a single `createProjectV2(input:{ownerId,title,repositoryId})` mutation. **This supersedes the 2026-08-11 ruling for `brainstorm.md` only** — `/analyze-issue` and `/letsgo` still treat a bare numeric first argument as a GitHub issue number.
Rationale: Projects start as Notion briefs, not as pre-written light spec files, so the workflow had no front end for turning a vision into trackable work. Grilling in rounds (whole frontier at once, each question carrying a recommended answer) closes the misalignment gap before any spec is written. Keeping issues light preserves the existing contract that deep specification is generated on demand, and closing the loop through issue numbers means `/letsgo <N>` already materializes `specs/<N>.md` with no new plumbing. `createProjectV2` accepts `repositoryId`, so create-and-link is one mutation rather than two calls.
Alternatives considered: (1) A separate `/brainstorm-project` command — rejected; the user wanted one entry point, and mode detection by input shape keeps the surface minimal. (2) A `--project` flag on `/brainstorm` — rejected as redundant once legacy input modes were dropped entirely. (3) A git-tracked `specs/{PROJECT}-vision.md` — rejected in favour of Engram-only; accepted trade-off is that the vision rationale is single-machine and invisible to a fresh clone, with the GitHub issues serving as the shared contract. (4) Native GitHub sub-issues via `addSubIssue`, or a ProjectV2 `Blocked by` custom field — rejected; body text needs no extra permissions and `/analyze-issue` inherits the dependency graph for free when it materializes the issue body. (5) An epic issue holding the vision — rejected; the board stays work-only. (6) Caching the Project number in a config file — rejected as a staleness risk for one cheap GraphQL call. (7) A reusable `skills/grilling/SKILL.md` — rejected; the protocol is inlined in `brainstorm.md` because subagents cannot converse with the user, so the interview cannot be delegated.
Scope: repo-wide — affects `brainstorm.md`, `AGENTS.md` Rule 1, `README.md`, `skills/spec-driven-workflow/SKILL.md`

## 2026-10-10 — /letsgo --base flag: ref-form contract and default-path freeze

Issue: 9
Decision: The `--base <branch>` flag on `/letsgo` resolves once (Step 0 parse + Step 0.1) into two variables: `BASE_BRANCH` (bare branch name, normalized — a leading `origin/` is stripped) and `BASE_REF` (`origin/<branch>`). Git plumbing (checkout start-point, `merge-base`, diff/log) must consume `BASE_REF`; `gh pr create --base` must consume the bare `BASE_BRANCH`; branch-equality checks (Step 8b.5) compare bare names. When `--base` is omitted, all four affected steps (0.1, 6, 8b, 8e) keep their current `origin/HEAD` derivation **byte-identical** — no fetch and no explicit start-point are added to the default path. The flag lives only in `/letsgo`; standalone `/review-code`, `/create-pr`, `/handover` retain their own derivations until a future issue propagates the flag.
Rationale: gh resolves PR targets server-side and misbehaves on `origin/<name>` values, while git plumbing needs the remote-tracking ref to be correct for remote-only branches (e.g. `ai/integration` never fetched locally) — hence the deliberate two-variable split. The default-path freeze is a hard acceptance criterion (AC4): `/letsgo` runs unattended in scheduled pipelines, and any silent behavior change on the omitted-flag path (extra fetch, changed start-point) risks existing AI Software Factory runs.
Alternatives considered: (1) One variable holding `origin/<base>` always, stripped for gh — rejected; silent string surgery at each consumer is drift-prone in LLM-interpreted markdown. (2) Also change the default path to `git checkout -b $FEATURE_BRANCH origin/$BASE_BRANCH` (fixing the pre-existing banner/behavior mismatch at letsgo.md L107 vs L109) — rejected for this issue; violates AC4, deserves its own light spec. (3) Propagating `--base` to `/review-code` and `/create-pr` in the same change — rejected; out of scope per light spec, and those commands are invoked standalone where a flag would need separate parsing.
Scope: subsystem `commands/letsgo.md`; the ref-form + freeze convention binds any future `--base` propagation to commands sharing the `git symbolic-ref refs/remotes/origin/HEAD` idiom (`review-code.md`, `create-pr.md`, `handover.md`)

## 2026-10-10 — /letsgo result.json driver contract and every-exit invariant

Issue: 10
Decision: `/letsgo` writes `specs/issue-{ISSUE_KEY}-result.json` at **every** exit point — 17 enumerated (16 stops E1–E16 + success E17), covering interactive stops (human reject, [S] choices, declined commit confirmation), not only headless stops. The schema is frozen to the light spec's 7 fields (`issue`, `outcome`, `stage`, `reason`, `branch`, `pr_url`, `pipeline{spec_turns, impl_passes, fix_passes}`); no field may be added without a driver-side change. Analyst rulings recorded here: (1) `issue` is a JSON number when `ISSUE_KEY` matches `^[0-9]+$`, else a JSON string; (2) the `pipeline` key is **absent** (not `{}`/null) when no counter has been initialised (exits before Step 1); (3) `branch`/`pr_url` use empty strings, never null, when unavailable; (4) write-before-stop ordering — the file is written immediately before the stop message prints, so it exists even if the session dies mid-message; (5) last-run-wins overwrite semantics; (6) standing invariant: any future stop added to `/letsgo` must carry a result.json hook per `## Step R — Result Contract`.
Rationale: The auto-flow driver reads outcome/stage/PR URL without parsing logs; the value is complete exit coverage — one missed exit means the driver sees `no_result` for a run that actually terminated. Freezing the schema protects the external driver boundary. Write-before-stop guarantees the artifact survives message-print failures.
Alternatives considered: (1) hooks only at headless stops (literal user-story reading) — rejected; the Goal says "every exit" and interactive coverage is nearly free. (2) A `test_fix_passes` counter for the Step 5b/7.5 test-fix loops — rejected; the schema is the driver's contract, not ours to extend unilaterally. (3) Mapping the Step 7.5 post-review test failure to `stage="review"` — rejected; the failing gate is the test gate, so `stage="tests"` with `reason` recording "post-review". (4) Hard enforcement via an OpenCode plugin (`tool.execute.before`) — deferred; prompt-level hooks + the `tests/verify-letsgo-result.sh` harness assertions suffice for v1, with plugin enforcement as the escalation path if drift appears in real runs.
Scope: subsystem `commands/letsgo.md` + the external auto-flow driver contract (`specs/issue-*-result.json`); binds every future change to `/letsgo` exit points

## 2026-10-28 — /brainstorm routes slices to the Foundry or the human lane

Issue: n/a (project-level brainstorm / Code Foundry integration)
Decision: `/brainstorm` keeps publishing light GitHub issues, but now classifies every slice with a `## Foundry fit` block (`Fit: yes|no`, `Why`, `Needs before Ready`, `Verification`) and primes the Project Status explicitly after `item-add`. `Ready` means **Fit: yes AND every blocker closed/Integrated AND every `Needs before Ready` satisfied AND the user confirmed the slice in the Step 4 quiz**; everything else goes to an intake status (`Backlog` if the board has it, else `To Do`/`Todo`). The command never sets `Blocked` or `In Progress` at creation. Foundry-fit candidates that are still blocked or missing a prerequisite stay in intake with manual promotion; the report prints the exact `gh project item-edit` command and splits the output into Foundry queue, human lane, and waiting-on-blockers. `Fit` is a property of the slice; `Ready` is a board state, so a slice can be `Fit: yes` while `Needs before Ready: make ci exists on ai/integration` and remain in intake. Foundry-fit issue bodies are self-contained: they inline a short vision excerpt in `## Context`, because the Foundry sandbox cannot reach Engram. Engram persistence remains best-effort for the human session. The command uses the real project owner (`PROJECT_OWNER` from the project node/URL, not necessarily the repo owner) and provisions a missing `Status` field, or adds missing options with explicit user consent; it never silently mutates an existing board schema. No `foundry-fit` label is used; status plus the body block is the contract for v1. This extends the 2026-10-09 ruling; the Notion-URL-only input, tracer-bullet rules, and `## Blocked by` text convention are unchanged.
Rationale: The Foundry picks only `Ready` issues by board position (`driver/__main__.py:390-407`) and requires exact Status option names (`driver/gh.py:338-362`), while `item-add` alone lands an item in the board default. Without explicit routing and status priming the command produces issues the Foundry can never pick up. Engram is not visible from the sandbox today (no MCP config; only `auth.json` is mounted; `Dockerfile:8` defers it), and a future remote VM is expected to have its own Engram, so duplicating a short vision excerpt into the issue body is the portable v1 contract. Defaulting to the human lane and requiring explicit confirmation keeps the soft rubric conservative and avoids sending product decisions or infra work into a headless run.
Alternatives considered: (1) Implement Engram injection into the sandbox now — deferred; it is substantial Linux-client/MCP-bridge/network work with no clear advantage once the VM has its own Engram, and visibility alone would not make `/letsgo` search it. (2) A dedicated `Human` status — rejected; the existing intake status (`Backlog`/`To Do`/`Todo`) is sufficient and avoids a schema change. (3) Auto-promotion of blocked slices — deferred to a separate `code_foundry` issue; manual promotion is the v1 contract. (4) A `foundry-fit` label — rejected for v1; the driver ignores labels, and a body-based pick guard is the better enforcement path if one is added. (5) Strict `Fit: no` until `make ci` exists — rejected; provisional `Fit: yes` plus `Needs before Ready` keeps a greenfield roadmap plannable without erasing the routing decision.
Scope: repo-wide — affects `commands/brainstorm.md`, `AGENTS.md` Rule 1, `README.md`, `skills/spec-driven-workflow/SKILL.md`; the `## Foundry fit` block and status contract bind future `/brainstorm` changes and the corresponding `code_foundry` preflight/pick-guard issues.

## 2026-10-29 — /letsgo Foundry mode: activation gate, draft-PR mutex, land contract

Issue: 13
Decision: `/letsgo` gains a Foundry mode active **only** when `--headless` AND `--base <branch>` are both present (`FOUNDRY_MODE = HEADLESS && BASE != null`); the interactive path is byte-identical. The mode owns a fixed lifecycle: fail-closed **preflight** on the live GitHub body (`## Foundry fit` `Fit: yes`; `## Blocked by` refs restricted to same-repo `#N` and external `OWNER/REPO#N`; a ref passes on CLOSED/MERGED or — same-repo OPEN only — board `Status == Integrated`; project resolved via `repository.projectsV2` with exactly-one rule) → **board claim** `In Progress` before any branch/commit/push → **branch** `feat/<N>-<14-digit-timestamp>` from `origin/<base>` with a hard stop (never reuse) if already on a non-base branch, plus a unique-match RESUME_CHECK against open `feat/<N>-*` PRs → **draft-PR mutex** (empty commit → sensitive-scan → push → `gh pr create --draft`) as the concurrency lock → existing pipeline with **scan-before-every-push** checkpoint pushes (never force) → **land** via `gh pr edit` → conditional `gh pr ready` → exactly one strategy: `--merge-mode auto` (default) arms `gh pr merge --auto --merge`, `--merge-mode direct` runs `gh pr merge --merge`. Every exit writes the frozen-schema `result.json` (new hooks E18–E23 + E17-F registered in Step R) and upserts exactly one `<!-- opencode-flow:result -->` marker comment (find→PATCH, else create). Any post-mutex stop closes the PR and sets `Blocked`. The command **never** writes `Integrated`, never composes `--squash`/`--rebase`, never retries a failed merge with another strategy, never adds `Closes #N` to PR bodies, and bounds every external call with a timeout.
Rationale: The Code Foundry host reconciler must only decide *when* to tick, not *how* work is done; a headless run needs a pre-write eligibility gate (fail closed), a queue lock that survives crashes (the early draft PR is the mutex — PR creation moves from terminal Step 8e to Step 0.8), and safe re-entry (resume the existing branch/PR, never duplicate). Merge truth and `Integrated` belong to the reconciler because auto-merge is asynchronous and no agent is alive at merge time; the result.json schema stays frozen so the driver contract is untouched. Close-on-stop prevents the mutex from deadlocking the queue.
Alternatives considered: (1) Squash/rebase merge modes — rejected; merge commits only, per the reconciler's batch-integration model on `ai/integration`. (2) Writing `Integrated` after arming auto-merge — rejected; the merge may never complete, so only the reconciler may claim integration. (3) Reusing the checked-out non-base branch (current Step 0.1 behavior) — rejected for Foundry mode; unsafe under concurrent hosts, replaced by hard stop + resume-detection. (4) Keeping PR creation terminal (Step 8e) — rejected; a late PR gives no mutex, so two hosts could pipeline the same issue. (5) A shared board-write helper/skill now — deferred; canonical `gh project` command blocks in `letsgo.md` reuse the `brainstorm.md` idioms, and a shared surface is a candidate follow-up issue. (6) New `outcome`/`stage` enum values (e.g. `merged`) — rejected; the result contract is frozen and merge truth is not the agent's to report.
Scope: subsystem `commands/letsgo.md` (+ push-governance rule in `agents/spec-implementer.md`, `README.md` paragraph, `tests/verify-letsgo-foundry.sh`); binds every future change to `/letsgo` exit points, board writes, and the `--base`/`--headless` flag surface; interacts with decisions 2026-10-06 (hardening), 2026-10-10 (`--base` ref-form + result.json freeze), 2026-10-28 (Foundry fit/status contract)

## 2026-10-29 — Shared Foundry surface is a skill (`foundry-headless-contract`), loaded by headless commands

Issue: 14
Decision: The canonical board + result-comment surface for headless Foundry commands is a **skill** at `skills/foundry-headless-contract/SKILL.md` (not a hidden agent), defining four operations — F1 project discovery (`repository.projectsV2`, exactly-one, never cached, fail-closed with zero writes), F2 status write (field precheck → GraphQL current-status read → no-op if already target → exact case-sensitive `gh project item-edit --field "Status" --value "<name>"`; never creates/renames options; never writes `Ready`/`Integrated`), F3 idempotent `<!-- opencode-flow:result -->` comment upsert (find→explicit `-X PATCH`, else create; token hygiene; independent of F1), and F4 the headless `gh` allowlist — which **must include `gh api *`** alongside `gh project`/`gh pr`/`gh issue`, because F1/F3 execute through `gh api`. Consumers carry the exact load line `Load skill: foundry-headless-contract` and contain no inline board/comment recipes; the verification harness pins load-line presence, recipe absence in consumers, and executes the skill's `$`-variable bash recipe blocks against a fake-`gh` shim. Rulings: (OD1) since `/review-pr` is a separate future issue, AC1 is enforced by a consumer-glob assertion that auto-covers `review-pr.md` when it lands; (OD2) "zero comments" on unresolvable project constrains the **surface** (no side-effect comments from a failed F1) — command-level result-comment mirrors on their own stop hooks (e.g. `/letsgo` E19) keep the frozen issue-13 behavior.
Rationale: Commands are LLM-interpreted governors; the repo's shared-prose-contract idiom is `Load skill:` (AGENTS.md Rule 2). A hidden agent would route deterministic lifecycle writes through subagent dispatch, losing the governor's variable bindings and adding failure modes. Skill recipes written as executable bash make AC2/AC3 behaviorally testable (fake-`gh` shim) instead of prose-only. Discharges the deferred "shared surface is a candidate follow-up issue" from decision 2026-10-29 (issue 13).
Alternatives considered: (1) Dedicated hidden agent — rejected: dispatch overhead, context loss at claim/stop points, subagents can't share governor state. (2) Bash helper library sourced by commands — rejected for v1: commands interpret markdown, not shell libraries; the executable-recipe-in-skill pattern gets the same testability without a new runtime layer. (3) Refactoring `/brainstorm` onto the surface — rejected: explicitly out of scope (findings); `/brainstorm` provisions interactively (may create fields/options) while the surface is headless fail-closed — different contracts, so `brainstorm.md` keeps its inline recipes and is exempt from the consumer glob. (4) Narrowing F4 to the three families the light spec lists — rejected: breaks the headless path on the first `gh api graphql` discovery call.
Scope: repo-wide — `skills/foundry-headless-contract/` (mirrored to `~/.config/opencode/skills/` per the 2026-10-19 mirror convention), `commands/letsgo.md` load line, `tests/verify-foundry-surface.sh` + redirected `tests/verify-letsgo-foundry.sh`; binds the future `/review-pr` command issue and any headless command touching board status or result comments; the Foundry sandbox image (`code_foundry`) must ship the skill.

## 2026-10-29 — /review-pr repair loop: bucket polling, F3-comment verdict memoization, never-close ownership

Issue: 15
Decision: `commands/review-pr.md` (headless, `model: opencode/qwen3.6-plus`) repairs red Foundry PRs under three cross-issue rulings. (1) **Polling contract:** check state is read from `gh pr checks --json name,bucket,link` bucket values (`pass`/`fail`/`pending`/`skipping`), never from the process exit code; each poll cycle is bounded by a wall-clock `--deadline` (default 900 s, interval 60 s) and `--watch` is forbidden; pending-at-deadline is a non-terminal, non-memoized stop that mutates nothing. (2) **Verdict memoization without new state:** terminal exhaustion verdicts are memoized in the existing F3 marker comment — `reason` carries a `head <SHA>` token compared against `headRefOid` on re-entry; no new artifact, no `result.json` write (that file stays `/letsgo`-owned and schema-frozen), no cross-invocation attempt accounting (the ticker owns scheduling). (3) **Ownership inversion vs `/letsgo`'s FSP:** `/review-pr` never closes the PR, never merges with a retried strategy, never writes `Ready`/`Integrated`/`In Progress` — its only board write is `Blocked` via F2, and at exhaustion the PR is deliberately left OPEN for the reconciler; when no linked issue resolves (branch `^feat/<N>-` first, then PR-body `Related Issues #N`), it degrades to a zero-write summary exit. Commit governance is inverted from `/letsgo`'s "subagents commit": reviewer/fixer dispatches carry an explicit no-commit/no-push directive and the governor creates exactly one commit per attempt (verified via `git log SHA_BEFORE..HEAD` count), because the one-commit-per-attempt cap cannot be enforced if subagents commit independently. Reviewer dispatch is inlined (commands cannot invoke commands) with `/review-code` Step 3–4 prompt shapes plus a bounded failing-log context block (`gh run view --log-failed`, `tail -c 20000`).
Rationale: The reconciler ticks `/review-pr` repeatedly on the same PR; without memoization every tick re-spends the full attempt budget on an already-diagnosed head SHA, and without bucket-based pending detection a slow CI run is misread as red (gh exits non-zero while checks run). Closing the PR would destroy the `/letsgo` mutex artifact `/review-pr` does not own; leaving it OPEN keeps the reconciler's state machine authoritative. The frozen 7-field comment vocabulary is reused (reason-as-memo-key) precisely because the driver contract must not be extended unilaterally (issue-10 precedent).
Alternatives considered: (1) A `specs/issue-<N>-review-pr-state.json` artifact for attempts/verdicts — rejected: invents a second state file next to the frozen result.json and reopens the "durable cross-invocation accounting" explicitly scoped out by the light spec. (2) Reusing exit codes of `gh pr checks` for red detection — rejected: conflates pending with failing, violating AC2. (3) Letting fixer subagents commit as they do under `/letsgo` — rejected: breaks the "each pushes at most one commit" AC; governor-owned commit keeps the cap enforceable. (4) `/review-code` invocation instead of inline dispatch — impossible per `letsgo.md` L13–14 (commands cannot invoke commands). (5) Closing the PR at exhaustion like the FSP — rejected: `/review-pr` never created the mutex; close would evict in-flight work from the reconciler's queue.
Scope: subsystem `commands/review-pr.md` + `tests/verify-review-pr.sh`; binds the host reconciler (`code_foundry`) tick semantics, any future command that polls `gh pr checks`, and the `foundry-headless-contract` surface (review-pr is its second consumer); interacts with decisions 2026-10-29 (issue 13 land/FSP, issue 14 surface), 2026-10-10 (result.json freeze, `--base` ref-form), 2026-10-19 (model routing).
